## How To Test

**Node tests** (need Node.js; players do not):

```bash
node tests/run-tests.js
```

About two minutes. Runs unit tests (combat rules, saves, settings, data integrity, schema of every character), every Combat Lab scenario headless, fighter-system tests, the human-playtest regression tests (flight, targeting, group pressure), per-character kits, boss and giant systems, telemetry, the `.glb` pipeline, battle rules, the radial menu, party battles, a regression sweep that starts every mission from every checkpoint, and story missions played by bots that only send player inputs (`tools/mission_brains.js`). Engine tests use fixed random seeds. `node tests/run-tests.js --fast` skips the engine tests.

**Combat Lab (in the browser):** open the game, press F12, run
`const s = document.createElement('script'); s.src = 'tools/lab.js'; document.body.appendChild(s);` then `SLLab.runAll().then(r => console.table(r))`. (The same scenarios also run headless inside the Node suite.)

**Balance duel (CPU vs CPU, telemetry):** `node tools/balance_duel.js goku vegeta 40 normal 1` — add `--tweak=noMech` (or `mechSwap`, `kitSwap`, `specialsSwap`, `statSwap`, `aiSwap`, `bodySwap`, `noIT`, `noKaioken`, `noForms`…) to remove one suspect at a time. CPU-vs-CPU finds broken behaviour; it is **not** human balance.

**Boss / swarm balance sims:** `node tools/balance_boss.js nappa goku 6 normal [cpu|reader]` · `node tools/balance_saibamen.js goku 3 6`.

**Encounter readability probe:** `node tools/encounter_probe.js <missionId> <startPhase> [seconds] [seed] [novice|average]` — plays a story phase with a simple human-like bot (4 runs; in party battles it follows hero switches and reports the share of enemy damage taken by the controlled hero versus CPU allies) and reports damage per 10 s, hits from outside the camera view, how many enemies hit within 2 s, the longest hit chain, enemy blasts per 10 s, time stunned and outcomes. Example: `node tools/encounter_probe.js prologue_final_stand 1 90 1 novice`.

**GLB check:** `node tools/glb_check.js model.glb [--write-js] [--id name] [--height 1.85] [--facing 180] [--map jointmap.json] [--json]` — checks and packages a real model (`assets/models/README.md`). `node tools/make_test_glb.js` regenerates the test mannequin.

**Browser checks:**
- `SL.dataProblems` in the console lists schema problems found at boot (empty = valid).
- `tools/viewer.html?char=ID&pose=stand` — model and pose viewer.
- `tools/snap.js` (load like the lab) — freeze moments and place the camera for visual checks.
- `tools/missionbot.js` (load like the lab) — `await MissionBot.run('saiyan_kingkai', { timeoutSec: 240 })` plays a mission with the bot brains.
- `SL.debugAutopilot = 'hard'` — the CPU plays the player's fighter.
- `SL.Telemetry.history()` — the last 40 battles in this browser.
- When a browser tab is hidden, `requestAnimationFrame` stops: drive frames manually (`SL.App.battle.update(1/60)` in a loop, then `render()`) and send real `KeyboardEvent`s to `window` to test input paths.

**Human playtesting:** use the checklists in `STATUS.md` → *Human playtest checklists*. Record what a person actually observed in `STATUS.md` → *Human playtest findings* and in *Human Playtest Findings* below — never mixed with automated results.

## Asset Blockers

**BLOCKED BY ASSETS** means code alone cannot produce it at good quality; it is different from **not implemented** (which code can build).

| Blocked by assets | Why | Current stand-in |
|---|---|---|
| Production 3D character models (Level 3) | Sculpted faces, muscles, clothing folds, hair volume and textures need a 3D artist. | Level 1–2 procedural prototype bodies. The `.glb` pipeline is ready to import them. |
| Hand-keyed or motion-captured animation | Weight, overlap and timing at anime quality need an animator. | Pose-to-pose animation with springs and squash/stretch. |
| Facial rigs / morph targets | Need model-side setup. | Procedural faces with eleven expressions (procedural bodies only); the quiet smile in the prologue ending is an approximation. |
| Voice acting | Needs actors; must never be ripped from the anime or games. | Subtitle-only lines. |
| Composed music | Needs a composer. | Synthesized music in code. |
| Recorded sound design | Needs a sound designer. | Synthesized SFX in code. |
| Detailed environments (cities, Kame House, Namek) | Need environment art. | Procedural terrain, rocks, trees, sky moods. |
| Artwork for gallery, loading screens, portraits | Needs illustrators. | None (no gallery exists). |

**Not implemented (buildable in code, not blocked):** Dragon Balls and Shenron, fusion, the custom character (the customization foundation exists since 2026-09-24), tournaments, Boss Rush, gallery screens, secret menu progression, original Dragon Ball chapters, Namek onward, playable Great Ape, weather, time of day, desktop packaging.

No outside asset has been downloaded or used except three.js r149 (approved; MIT licence in `vendor/three.LICENSE.txt`).

## Current GLB Pipeline

**FUNCTIONAL PROTOTYPE — proven with an original test mannequin only; no real character model exists yet.**

- **Works:** in-house glTF 2.0 binary reader (`src/render/glb.js`); skinned meshes, materials, embedded base color textures, skins, animation clips; name-based or explicit joint mapping to the 17-joint rig; every game pose retargeted onto the file's bones (`src/game/model_glb.js`); sockets for beams, props and hit sparks; outlines, rim light, hit flash, afterimages, HUD portrait; base64 `.glb.js` twin for `file://`; checker and packager `tools/glb_check.js`; verified in battle at 60 fps with two imported fighters.
- **Not supported yet:** morph targets (faces), per-form hair swaps (Super Saiyan), hand shapes, stretching limbs, cloth springs on imported bodies, normal/emissive/metal-roughness maps.
- **To add a real model:** follow `assets/models/README.md` (check → `--write-js` → `<script>` in `index.html` → `model: { type: 'glb', asset, height, jointMap, production: true }` → raise `assetLevel` to 3 → viewer → tests). Only with a model the owner made, commissioned or licensed, and explicitly approved.

## Development Workflow

```
READ → UNDERSTAND → BUILD → PLAY → OBSERVE → IDENTIFY → FIX → TEST → REGRESSION → POLISH → UPDATE DOCUMENTATION → CONTINUE
```

- **Read / understand:** the four documents, then the code you will touch and its tests.
- **Build** the highest-priority item in small, integrated steps.
- **Play / observe:** run it in the browser (or headless with a probe/bot) and look at what actually happens.
- **Test:** add behavioural tests; run `node tests/run-tests.js`; nothing merges with failures.
- **Regression:** check earlier features still work (the suite includes every mission from every checkpoint).
- **Human playtest checklist:** every new major gameplay system gets a short checklist in `STATUS.md`.
- **Update documentation:** `HANDOFF.md` and `STATUS.md` whenever a major system changes, `README.md` when running or controls change, `MASTER_SPEC.md` only when the long-term specification itself changes. Do not duplicate contradictory information.

3. Run `node tests/run-tests.js` first to confirm the baseline (expect all tests to pass; the count is in *Latest Test Results*).
4. Open `index.html` in a browser (or `node tools/serve.js`) and look at the game before modifying it.
5. Respect the standing constraints: local only, no Git, no uploads, no outside assets without approval, frozen builds untouched.
6. Start with *Immediate Next Task*. Keep human findings and automated results separate. Report honestly using the status words in `STATUS.md`.
